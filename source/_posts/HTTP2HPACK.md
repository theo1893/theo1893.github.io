# HPACK算法

HPACK是HTTP2中用于压缩HTTP Header的算法. 在正式介绍HPACK算法前, 我们还需要看一下HTTP/2对部分现存Header的协议层处理: 新的Pseudo-Header, 以及Cookie的切分.



## Pseudo-Header

HTTP/2引入了几个特殊的Pseudo-Header, 用于传递URI, 请求方法, 状态码等数据. 这些字段格式和HTTP/1.x不同, 用于区分.

| Pseudo-Header | Meaning                          |
| ------------- | -------------------------------- |
| :method       | 请求头. 用于传递HTTP方法: GET, POST, ... |
| :scheme | 请求头. 用于传递协议头: http, https |
| :authority | 请求头. 用于传递host, 比如example.com |
| :path | 请求头. 用于传递path, 比如/demo/get?q=1 |
| :status | 响应头. 用于传递状态码 |



## Cookie

HTTP/2[建议](https://datatracker.ietf.org/doc/html/rfc7540#section-8.1.2.5)把Cookie按照 **;** 拆分为更小的项. 在Golang的HTTP/2实现中, Cookie被完全按照 **;** 拆分为单独的项:

``` 
// 原始cookie串
cookie: A=a1; B=b2; C=c1; D=d1

// HPACK编码后的header entry
cookie: A=a1
cookie: B=b1
cookie: C=c1
cookie: D=d1
```



## HPACK基本编码

HPACK中使用了2种基本编码: 整型编码和字符串编码. 详细文档参考 [RFC7541](https://httpwg.org/specs/rfc7541.html#low-level.representation).



### 整形编码

HPACK的整型编码需要指定1个参数: 前缀长度N. N表示整数会按照多细的粒度被写编码进字节流.下图展示了前缀N=5的2种编码情况.

![](int_intro.png)



这里我们用一个例子来解释. 假设N=7, 且首字节的前8-N个bit为0:

对小于127的整数, 编码使用1个字节存储, 最高位0, 剩余位数为二进制位.

对大于等于127的整数, 编码使用多个字节存储, 分为3个部分:

1. 首字节固定为127;

2. 中间多个字节的首位固定位1, 剩余7位存储7个有效位;

3. 尾字节存储剩余有效位;

其编码流程如下图所示:

![](int_encode_process.png)



具体编码格式如下图所示:

![](int_encode.png)



解码操作即为这里的逆流程, 读取字节流将其中的payload重新组装为整数, 相应的细节在net/http2/hpack/hpack.go.



### 字符串编码

HPACK对字符串的编码数据如下图所示:

![](string_intro.png)



编码数据由2部分组成: 

1. 前N个字节是使用前缀长度=7为参数的长度编码; 第1个字节的第1个bit标记字符串是否使用Huffman编码.
2. 后M个字节是具体的字符串数据.



在对字符串进行编码时, HTTP/2会进行一次预判: 如果使用Huffman编码后字符串长度更短, 则会使用Huffman, 否则使用原始字符串. 

这里以字符串`hello,world`为例, 字符串原始长度为11Byte, 编码后的长度为9Byte, 编码长度占优, 因此使用编码数据.

![](string_encode.png)



补充: HTTP/2的标准提案遵循一套预定义的霍夫曼[编码表](https://httpwg.org/specs/rfc7541.html#rfc.section.B), 所有实现方均使用这张编码表:

``` go
// 编码表
var huffmanCodes = [256]uint32{
	0x1ff8,
	0x7fffd8,
	0xfffffe2,
	0xfffffe3,
  ......
}

// 编码长度
var huffmanCodeLen = [256]uint8{
	13, 23, 28, 28, 28, 28, 28, 28, 28, 24, 30, 28, 28, 30, 28, 28,
  ......
}
```



## 静态表/动态表查找

HTTP/2标准预定义了一张包含61个常用Header的[静态表](https://httpwg.org/specs/rfc7541.html#rfc.section.A), 以及一张初始为空, 最大占用4096B的动态表. 这是HTTP/2减小Header传输压力的核心设计.

协议规定, 静态表和动态表共享一个索引空间, 下图展示了静态表长度为s, 动态表长度为k的索引空间分布:

![](table_intro.png)



在具体实现中, 静态表和动态表**均由2部分组成**: 需要同时匹配Header-Value的完全匹配表, 以及仅需要匹配Header的部分匹配表.

当一个HTTP Header同时命中Header-Value时, 这里称为**完全命中**; 当仅命中Header, 而没有命中Value时, 这里称为**部分命中**.

下面对查询结果分情况讨论.



### 完全匹配

在完全匹配的场景下, 发送方和接收方已经对这个Header完全达成共识, 因此发送方可以直接将命中的索引id编码后写入字节流, 由接收方自行索引.

![](full_match.png)

协议规定此场景下整型编码索引前缀**N=7**, 同时, 编码的首字节会执行 |= **0x80**, 用于标记完全匹配. 

最终编码长度为1字节.



### 部分匹配

部分匹配涉及到2个子场景: 需要更新动态表的场景, 不需要更新动态表的场景.



#### 更新动态表

当Value不是敏感数据, 并且这个Header的大小未超过动态表的单条记录大小限制时, 发送方会将Value写入本地动态表, 并通知接收方更新远端动态表.

具体地, 发送方会将匹配得到的**旧索引**以及Value进行特殊编码, 写入字节流. 接收方本次查询使用**旧索引**, 同时更新本地的动态表. 

![](partial_match_w_index.png)

此场景下, 整型索引前缀**N=6**, 编码的首字节会执行 |= **0x40**, 用于标记动态表发生更新. 

最终编码长度为7字节.



#### 不更新动态表

当前一场景的任一条件未满足时, 退化到不更新动态表的流程. 假设Value是敏感数据, 导致不更新动态表, 流程区别发生在:

1. 发送方和接收方不会更新本地动态表;
2. 发送方发送的索引编码**N=4**, 首字节执行 |= **0x10**;

流程图如下图所示, 最终编码长度为6字节.

![](partial_match_wo_index.png)



### 未命中

未命中同样涉及到2个子场景.



#### 更新动态表

在此场景下, 发送方会将这一组Header-Value写入动态表, 并将Header和Value进行编码, 写入字节流.

![](full_miss_w_index.png)

和部分匹配不同的是, 由于这里没有发送索引, 因此发送方会在最终编码的头部额外增加一个字节 = **0x40**, 用于标记动态表更新.

最终编码长度为19字节.



#### 不更新动态表

如果未命中, 并且不更新动态表, 发送的数据和更新动态表基本一致, 区别仅在于额外增加的首字节: 这里额外增加的首字节是**0x10**, 而非0x40. 

最终编码长度为19字节, 此处不单独画图.



## 动态表更新

上文我们提到, 在对Header编码时, 在查找动态表时, 如果只命中了Header或者完全未命中, 可能会将这个请求头写入本地动态表, 并通知远端服务器更新远端动态表. 

更新动态表的示意图如下图所示:

![](dt_update_process.png)

如果插入动态表后, 动态表的大小超出了限制(默认是4096 Byte), HPACK将循环移除早期表项, 直到表大小降到限制以下.

在Golang的实现中, 为了内存管理的效率, 并非直接按照协议规定组织表项, 而是逆向管理动态表, 在使用时将逆向的顺序映射到正确的空间索引中. 这里不做详细描述.
